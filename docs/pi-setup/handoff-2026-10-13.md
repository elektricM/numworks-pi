## Quick reference

- Calculators: the **N0100** is the NumWorks-Pi (Epsilon DFU serial GAAeAAFRNzI0NDU3, map 0x08000000). **Never flash the N0110** (GwAPABJQVllONDQg). In the Pi app the N0100 doesn't enumerate on USB.
- Build: `cd firmware && make MODEL=n0100 ENABLE_RPI=1 RPI_AUTOSTART=1 OMEGA_USERNAME="Martin" EPSILON_I18N=en -j8 output/release/device/n0100/epsilon.bin`, then check the size is ≤ 1048576.
- Stats: `ssh pi@10.37.9.37 nwpi-ctl stat` and `cat /sys/module/drm_spifb/parameters/{protocol,header_gap_us}`.
- Fall back to the legacy display: `sudo touch /etc/nwpi/display-legacy && sudo systemctl restart nwpid`.
- Desktop test load: `WAYLAND_DISPLAY=wayland-0 XDG_RUNTIME_DIR=/run/user/1000 setsid -f lxterminal -e top -d 0.2`.
- The kernel spins `cs_change_delay` ≤ 10 µs and `usleep_range`s above that (`fsleep`).

- **Camera cost, diagnosed (12:00–12:40).** The camera app hides the cursor, so labwc scans its fullscreen GPU buffer out directly (`imported=yes` in `/sys/kernel/debug/dri/1/framebuffer`). GPU buffers are mapped uncached for the CPU (about 60 MB/s), so reading 640x480 costs about 20 ms per frame. With the cursor visible, labwc composites and pays the same 22 ms instead; the total stays about 35 ms of CPU per frame (driver + labwc + app). SDL on Wayland always draws through the GPU, with or without `pygame.SCALED` (an earlier note blaming `SCALED` was wrong; `SCALED` does save the app's own CPU). Ruled out with measurements: NEON (the C path slows by the same 11x), the memory bus (userspace reads stay fast), the camera hardware, memory pressure, and a different buffer.
  - Tried: a DMA-engine copy of imported buffers into a cached bounce buffer (dma-buf attach to the channel's device). Not shipped; the patch is `dma-bounce.patch` in the session scratchpad.
  - Closed: reading GPU buffers through a cached alias. arm32 still remaps the linear mapping of CMA allocations (`__dma_remap`), and ARMv7 forbids mismatched cached/uncached aliases.
